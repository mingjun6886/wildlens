# Phase 10 CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run lint, tests, web build, Terraform validation and checkov on every pull request and push to `main`, and run a read-only `terraform plan` on pull requests that touch `infra/**`, authenticated to AWS by OIDC.

**Architecture:** `ci.yml` is a credential-free `check` job. `plan.yml` is a separate workflow, filtered to `infra/**`, that assumes a read-only IAM role created by a new Terraform module `ci`. CI never applies anything.

**Tech Stack:** GitHub Actions, Terraform 1.14 (AWS provider ~> 6.0), checkov, Python 3.11, Node, make.

**Spec:** `docs/superpowers/specs/2026-10-08-ci-design.md`

## Global Constraints

- English only in every file written. The pre-commit hook rejects Vietnamese characters (`git config core.hooksPath .githooks` must be set; check with `git config core.hooksPath`).
- Every third-party action is pinned to a full 40-character commit SHA with the version in a trailing comment.
- `ci.yml`: `permissions: contents: read` only. No secrets, no `id-token`.
- `plan.yml`: `id-token: write` and `contents: read` at **job** level, never workflow level.
- Role trust: `aud` equals `sts.amazonaws.com`; `sub` equals exactly `repo:mingjun6886/wildlens:pull_request`.
- `terraform plan` runs with `-lock=false -input=false -no-color`.
- State bucket: `wildlens-tfstate-895770859102`, key `dev/terraform.tfstate`. AWS account `895770859102`, region `ap-southeast-2`.
- Terraform `~> 1.14`; ruff line length 100; Makefile recipes use literal TABs.
- Do **not** run `terraform apply`, and do not push, without the owner's explicit instruction. Commits are made only in the steps that say so.
- Commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.

## Review Focus

- A pull request from a fork touching `infra/**`: `plan` must skip with a visible reason, not fail; `check` must still run. Pinned by the `if:` condition in Task 2 and checked by reading the rendered workflow with `actionlint`.
- `AWS_PLAN_ROLE_ARN` unset: `plan` must fail at the credentials step with a message that names the variable (Task 2 adds an explicit guard step).
- The role used from `main` or a tag: must be refused by the trust policy. Task 2 asserts the exact `sub` string in the plan output.
- `ReadOnlyAccess` reading user data: the deny statements in Task 2 must appear in the plan output.
- Clean runner without `torch`: `make test` must not fail on import. Task 1 reproduces this in a fresh virtualenv.

#
# This workflow holds no credentials and requests no permissions beyond reading
# the repository, so it is safe on pull requests from forks. The read-only plan
# that does need AWS lives in plan.yml, which is why that file exists separately:
# a `paths` filter here would also switch this job off.
name: ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@__SHA_checkout__ # __TAG__

      - uses: actions/setup-python@__SHA_setup_python__ # __TAG__
        with:
          python-version-file: .python-version
          cache: pip
          cache-dependency-path: |
            requirements-dev.txt
            ml/requirements.txt

      - name: Install Python dependencies
        # ml/tests/test_tagger.py imports torch and PIL, so the unit tests need
        # them. They do not need megadetector, which only model_loader.py
        # imports and no test covers. The CPU build of torch is a few hundred
        # megabytes rather than the gigabytes of the default Linux wheel.
        # Versions match ml/requirements.txt.
        run: |
          pip install -r requirements-dev.txt
          pip install pillow==12.3.0 numpy==2.4.6
          pip install torch==2.14.0 torchvision==0.29.0 \
            --index-url https://download.pytorch.org/whl/cpu

      - uses: actions/setup-node@__SHA_setup_node__ # __TAG__
        with:
          node-version: lts/*
          cache: npm
          cache-dependency-path: web/package-lock.json

      - name: Install web dependencies
        run: npm ci
        working-directory: web

      - name: Lint
        run: make lint

      - name: Python tests
        run: make test

      - name: Web tests
        run: make test-web

      - name: Web build
        run: make build-web

      - uses: hashicorp/setup-terraform@__SHA_setup_terraform__ # __TAG__
        with:
          terraform_version: 1.14.x

      - name: Terraform format
        run: terraform fmt -check -recursive infra/terraform

      - name: Terraform validate
        # -backend=false: validation needs the provider schemas, not the state,
        # so no AWS access is involved.
        run: |
          terraform init -backend=false -input=false
          terraform validate
        working-directory: infra/terraform/envs/dev

        run: |
          pip install checkov==__CHECKOV_VERSION__

`infra/terraform/modules/ci/main.tf` (use this provider **resource** form when Step 1 found no existing provider; if it found one, replace the resource with `data "aws_iam_openid_connect_provider" "github" { url = "https://token.actions.githubusercontent.com" }` and point `Federated` at `data.aws_iam_openid_connect_provider.github.arn`):

```hcl
# GitHub's token issuer. AWS validates the certificate chain itself, so no
# thumbprint is configured. There can be only one provider per URL per account.
resource "aws_iam_openid_connect_provider" "github" {
  url            = "https://token.actions.githubusercontent.com"
  client_id_list = ["sts.amazonaws.com"]
}

resource "aws_iam_role" "plan" {
  name = "${var.name_prefix}-ci-plan"

  # Exactly one subject: a pull_request run of this repository. A run on main,
  # on a tag, or in any other repository presents a different `sub` and is
  # refused. The workflow file can be edited by any branch, so this condition
  # and the policies below are the real controls, not the workflow.
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Action    = "sts:AssumeRoleWithWebIdentity"
      Principal = { Federated = aws_iam_openid_connect_provider.github.arn }
      Condition = {
        StringEquals = {
          "token.actions.githubusercontent.com:aud" = "sts.amazonaws.com"
          "token.actions.githubusercontent.com:sub" = "repo:${var.github_repository}:pull_request"
        }
      }
    }]
  })
}

# Enough for `plan` to refresh every resource type in use.
resource "aws_iam_role_policy_attachment" "read_only" {
  role       = aws_iam_role.plan.name
  policy_arn = "arn:aws:iam::aws:policy/ReadOnlyAccess"
}

resource "aws_iam_role_policy" "state_and_data" {
  name = "state-read-and-data-deny"
  role = aws_iam_role.plan.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        # Read, never write: the role cannot take the state lock, which is why
        # the workflow plans with -lock=false.
        Sid      = "ReadState"
        Effect   = "Allow"
        Action   = ["s3:GetObject"]
        Resource = "arn:aws:s3:::${var.state_bucket}/*"
      },
      {
        Sid      = "ListStateBucket"
        Effect   = "Allow"
        Action   = ["s3:ListBucket"]
        Resource = "arn:aws:s3:::${var.state_bucket}"
      },
      {
        # ReadOnlyAccess would otherwise let this role read every uploaded
        # image and every row in the table. `plan` needs resource metadata, not
        # user data. An explicit Deny overrides any Allow.
        Sid    = "DenyUserDataReads"
        Effect = "Deny"
        Action = [
          "dynamodb:GetItem",
          "dynamodb:BatchGetItem",
          "dynamodb:Query",
          "dynamodb:Scan",
        ]
        Resource = "*"
      },
      {
        Sid         = "DenyObjectReadsOutsideState"
        Effect      = "Deny"
        Action      = ["s3:GetObject"]
        NotResource = "arn:aws:s3:::${var.state_bucket}/*"
      },
    ]
  })
}
```

Create `.github/workflows/plan.yml`, filling the tokens from Task 1 Step 3:

```yaml
# A read-only `terraform plan` on pull requests that change infrastructure.
#
# It assumes a role that can read, but not write, the account and the state, so
# the worst a malicious workflow edit can do is read resource metadata. See
# modules/ci for the trust condition and the deny statements. Nothing in CI ever
# applies.
name: plan

on:
  pull_request:
    paths:
      - infra/**
      - .github/workflows/plan.yml

permissions: {}

jobs:
  plan:
    # Pull requests from forks are not issued an OIDC token, so the job would
    # fail at sign-in with a confusing message. Skipping it says why.
    if: github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      id-token: write
      contents: read
    env:
      PLAN_ROLE_ARN: ${{ vars.AWS_PLAN_ROLE_ARN }}
    steps:
      - name: Require the role variable
        run: |
          if [ -z "$PLAN_ROLE_ARN" ]; then
            echo "::error::Repository variable AWS_PLAN_ROLE_ARN is not set. See docs/runbook.md, 'Bootstrapping CI'."
            exit 1
          fi

      - uses: actions/checkout@__SHA_checkout__ # __TAG__

      - uses: hashicorp/setup-terraform@__SHA_setup_terraform__ # __TAG__
        with:
          terraform_version: 1.14.x
          terraform_wrapper: false

      - uses: aws-actions/configure-aws-credentials@__SHA_aws_credentials__ # __TAG__
        with:
          role-to-assume: ${{ env.PLAN_ROLE_ARN }}
          aws-region: ap-southeast-2

      - name: Init
        run: terraform init -input=false
        working-directory: infra/terraform/envs/dev

      - name: Plan
        # -lock=false: the role cannot write the lock file, by design.
        run: |
          terraform plan -lock=false -input=false -no-color 2>&1 | tee plan.txt
          {
            echo '## terraform plan'
            echo
            echo '```'
            tail -c 60000 plan.txt
            echo '```'
          } >> "$GITHUB_STEP_SUMMARY"
        working-directory: infra/terraform/envs/dev
```

```markdown
# 10. CI plans with a read-only OIDC role and never applies

**Status:** accepted · Phase 10 · 2026-10-08

## Context

Lint, tests, the web build and Terraform validation were run by hand. The design
document also required that CI hold no long-lived AWS keys. The estate is applied
and destroyed manually between sessions to protect the credit.

## Decision

Two workflows. `ci.yml` runs every check that needs no AWS and requests nothing
beyond reading the repository. `plan.yml` runs `terraform plan` on pull requests
that touch `infra/**`, assuming a role through GitHub's OIDC issuer.

The role can read the account and the state and write nothing. Its trust policy
accepts one subject, `repo:mingjun6886/wildlens:pull_request`, so a run on `main`,
on a tag or in another repository is refused. Two explicit denies remove the
ability to read uploaded objects and table rows, which `ReadOnlyAccess` would
otherwise grant.

| Considered | Why not |
|---|---|
| A deploy job after merge | The estate is often destroyed. A deploy would fail against nothing or recreate it and spend credit |
| Accuracy evaluation in CI | Needs 470 MB of weights and the answer-key images and takes minutes on CPU. It stays a manual step before changing `ml/` |
| `plan` on every pull request | Gives credentials to changes that cannot affect infrastructure |
| Plan output as a pull-request comment | Needs `pull-requests: write`. The job summary is enough |

## Consequences

**The workflow file is not a security boundary.** Any branch can edit it, so the
role's trust condition and policies carry the safety. That is why the data-read
denies exist even though `plan` never needs them.

**`plan` cannot take the state lock.** The role has no write access, so the
workflow plans with `-lock=false`. For one maintainer that is acceptable.

**After a `terraform destroy`, the plan lists the whole estate as new.** It is
accurate and noisy; the runbook says so.

**The first apply is manual.** The role does not exist until the owner applies it.

**The repository is public, so plan output is too.** It contains resource names
and ARNs, not secret values, since Terraform redacts sensitive attributes.
```
