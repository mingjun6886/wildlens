# Phase 10 — Continuous integration with a read-only OIDC plan

**Date:** 2026-10-08
**Status:** Draft, awaiting review
**Scope:** `.github/workflows/`, `infra/terraform/modules/ci`, documentation

---

## 1. Goal

Every pull request, and every push to `main`, runs the checks that today are run by hand. CI authenticates to AWS through OIDC federation, with no stored access keys (success criterion S6 in the design document). CI never changes infrastructure.

### Decisions already taken

| # | Decision | Reason |
|---|---|---|
| D1 | CI, checkov and a **read-only** OIDC role. No CD | The estate is applied and destroyed by hand between sessions. A deploy job would either fail against a destroyed estate or recreate one, and spend credit |
| D2 | Two tiers: a `check` job that needs no AWS, and a `plan` job that runs only when `infra/**` changes | Most pull requests touch Python or web code. They should be fast and should never hold credentials |
| D3 | Accuracy evaluation (`ml/eval/run_eval.py`) does **not** run in CI | It needs 470 MB of weights and the answer-key images, and takes minutes on CPU. It stays a manual step before changing `ml/` |
| D4 | No pull-request comments from `plan` | Avoids granting `pull-requests: write`. The plan goes to the job summary |
| D5 | Branch protection is described, not applied | It changes how the owner works on `main`, and it is a GitHub setting rather than repository code |

### Out of scope

CD or any `terraform apply` from CI; accuracy evaluation in CI; Dependabot; release tagging; a second environment.

## 2. Workflows

Two files, because a `paths` filter at workflow level would also switch off the `check` job.

### 2.1 `.github/workflows/ci.yml`

Triggers: `pull_request` and `push` to `main`. Permissions: `contents: read` and nothing else. No secrets, no `id-token`, so it is safe on pull requests from forks.

Job `check`, on `ubuntu-latest`:

1. Check out the repository; set up Python from `.python-version` with pip caching.
2. Install `requirements-dev.txt`, then CPU builds of `torch` and `torchvision` from the PyTorch CPU index, plus `pillow` and `numpy`, all at the versions pinned in `ml/requirements.txt`.
3. Set up Node with caching keyed on `web/package-lock.json`; `npm ci` in `web/`.
4. `make lint`, `make test`, `make test-web`, `make build-web`.
5. Set up Terraform `~> 1.14`. `terraform fmt -check -recursive infra/terraform`. `terraform init -backend=false` and `terraform validate` in `envs/dev` (no AWS access needed).
6. Run checkov against `infra/terraform`.

**Why CPU torch is needed.** `ml/tests/test_tagger.py` imports `torch` and `PIL`, and `requirements-dev.txt` provides neither. `make test` passes locally only because `.venv` already holds them; on a clean runner it would fail on import. The tests do not need `megadetector` (only `services/process/model_loader.py` imports it, and no test covers that file), so the heavy install is avoided. The comment at the top of `ml/requirements.txt` claims CI never downloads PyTorch and must be corrected to say CI installs the CPU build only.

**checkov policy.** The first run will report findings, because the project deliberately omits some practices (no VPC, no customer-managed KMS). Each finding is either fixed or skipped with `#checkov:skip=<ID>:<reason>` on the resource itself, with the reason in English and tied to an ADR or the design document where one applies. Whole check groups are never disabled.

### 2.2 `.github/workflows/plan.yml`

Trigger: `pull_request` with `paths: infra/**`. Job condition: the pull request's head repository equals `github.repository`, so fork pull requests, which are not granted an OIDC token, skip the job with an explicit reason instead of failing.

Permissions at job level: `id-token: write`, `contents: read`.

Steps: check out; set up Terraform `1.14.x`; assume the role named by the repository variable `AWS_PLAN_ROLE_ARN` using the AWS credentials action; `terraform init`; `terraform plan -lock=false -input=false -no-color`; write the output to `$GITHUB_STEP_SUMMARY`. `-lock=false` is required because the role cannot write the state lock file, by design.

### 2.3 Action pinning

Every third-party action is pinned to a full commit SHA with the version in a trailing comment. SHAs are resolved at implementation time, not guessed.

## 3. Infrastructure: module `infra/terraform/modules/ci`

Wired into `envs/dev/main.tf`. Inputs: project/environment prefix, GitHub `owner/repo`, state bucket name. Output: `plan_role_arn`.

| Resource | Detail |
|---|---|
| `aws_iam_openid_connect_provider` | `token.actions.githubusercontent.com`, audience `sts.amazonaws.com` |
| `aws_iam_role` `wildlens-dev-ci-plan` | Trust: federated principal is the provider; `aud` equals `sts.amazonaws.com`; `sub` equals exactly `repo:mingjun6886/wildlens:pull_request`. The role is unusable from `main`, from tags, and from any other repository |
| Policy attachment | AWS managed `ReadOnlyAccess`, enough for `plan` to refresh every resource type in use |
| Inline policy, allow | `s3:GetObject` on the state object and `s3:ListBucket` on the state bucket (`wildlens-tfstate-895770859102`). Read only, hence `-lock=false` |
| Inline policy, deny | On `*`: `dynamodb:GetItem`, `Query`, `Scan`, `BatchGetItem`, `PartiQLSelect`; `logs:GetLogEvents`, `FilterLogEvents`, `StartQuery`; `cognito-idp:ListUsers`, `AdminGetUser`. `s3:GetObject` and `s3:GetObjectVersion` with `NotResource` set to the state bucket's objects |

**Why the deny statements.** `ReadOnlyAccess` also permits reading every uploaded image and every row in the table. `plan` needs resource metadata, not user data, and the workflow file can be altered by any branch in the repository, so the role itself must be the control. Without the deny, "read-only" would still read production data.

**Single-role note.** This follows ADR 7 (one IAM role per function): the role has one purpose and does not double as a deploy role.

## 4. Bootstrap and failure behaviour

**Bootstrap.** The role does not exist until applied, so the first apply is manual: review `terraform plan`, run `terraform apply` with `AWS_PROFILE=wildlens`, then set the GitHub repository variable `AWS_PLAN_ROLE_ARN` to the `plan_role_arn` output. This is a real change to the AWS account and is performed by the owner, not by the implementing session. The procedure goes in `docs/runbook.md`.

**Estate destroyed.** After a `terraform destroy`, `plan` reports the whole estate as to-be-created. That output is accurate but noisy. It is documented in the runbook and not automated away.

**Failure cases.**

| Situation | Behaviour |
|---|---|
| Fork pull request touches `infra/**` | `plan` skipped; `check` still runs |
| `AWS_PLAN_ROLE_ARN` unset | `plan` fails at the credentials step; the message names the variable |
| Role trust or policy wrong | `plan` fails at assume-role or refresh; `check` is unaffected, since the tiers are independent |
| checkov finds a new issue | `check` fails; fix it or add a justified skip |

**Public repository.** Actions logs and job summaries are public. A plan contains resource names and ARNs but no secret values, because Terraform redacts sensitive attributes, and the account ID is already in `variables.tf`. Accepted.

## 6. Branch protection (described, not applied)

Making `check` a required status check on `main` blocks direct pushes. The implementing session provides the `gh api` command and the Settings path; the owner decides whether to apply it.

## 7. Verification

1. Before pushing: run every `check` step locally from a clean environment; install checkov in a temporary virtualenv outside the repository to obtain the real findings; lint workflows with `actionlint` if available.
2. The first pull request is the real test of `ci.yml`. The work is not reported done until it is green on GitHub.
3. `plan.yml` can only be verified after the manual bootstrap apply. Until then it is untested, and the hand-off says so.

## 8. Resolved and open items

**Resolved.** No Terraform resource reads object contents or table items at refresh time: `infra/terraform` contains no `aws_s3_object` or `aws_dynamodb_table_item`, and its only data sources are `aws_region`, `aws_caller_identity` and `archive_file`. The deny statements therefore cannot break `plan`.

**Still to confirm during implementation.**

- Whether the account already has a GitHub OIDC provider. The provider is unique per account and URL; if one exists, the module must reference it with a `data` source instead of creating it.
- The set of checkov findings, and which of them are skips versus fixes.
- Latest SHAs and versions of the actions used.
- The `archive_file` data source builds the API zip from `services/api` during `plan`; confirm the runner produces the same result without a prior build step.
